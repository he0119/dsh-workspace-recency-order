# Agent Note: 顺序改的是宿主那份工作区注册表

Status: implemented

## Problem

侧边栏的工作区列表要「最近用过的在最前」。但浏览器端拿到的只是一份快照：侧边栏按宿主里持久保存的
工作区顺序渲染，客户端没有改渲染顺序的接口——它能做的只有调 `workspaces.insertBefore()`，而那已经是
**往宿主那份顺序上写**。

所以真正的选择是：这个功能由谁负责维持顺序？如果客户端每次收到快照就重排一遍，宿主那份顺序会一直是
旧的，刷新、换设备、别的页面打开时看到的仍是原顺序，于是每个页面都要从头纠正一次。

## Decision

顺序由 **Host 端**维护：插件在宿主里监听 `api-session/activity` 与 `api-session/added`，算出目标顺序，
然后对工作区注册表调 `insertBefore(id, beforeId)` 把顺序真的改掉。客户端不参与排序，只把置顶列表
读写给宿主（见[置顶列表交给宿主](2026-11-14-pins-live-in-the-host.md)）。

写入按「一步一次移动」走：每一轮都重新 `list()` 读注册表，用 `nextMove()` 找出第一处错位，只发一次
`insertBefore`，最多重试「工作区个数」次。`src/order.ts` 的两个纯函数因此不碰任何服务，测试直接覆盖。

## Alternatives considered

**在客户端重排渲染。** 客户端没有排序接口；唯一能改外观的做法是整体替换 `sidebar.workspaces`，那会
同时丢掉搜索、拖动排序、工作区树与各种对话框——换来的顺序还只存在于当前页面。

**每次活动直接把整个顺序写一遍（`setOrder` 之类）。** 宿主只提供单次移动的接口。即使有批量接口，
一次写整份也意味着本地快照里的每个位置都会被覆盖，别人（用户拖动、别的页面）的并发改动会被无声地
抹掉。

**攒一份完整目标顺序、一次性对齐。** 同上：单次移动是唯一有并发语义的写入口，逐步纠正才让「别人刚
改过的位置」有机会被读到。

## Consequences

- 排序结果跨页面、跨重启都成立：宿主那份 JSON（`~/.dsh/storages/workspace.json` 的
  `global.workspaceIds`）就是唯一事实，见 [formats.md](../../../../docs/formats.md)。
- 代价是每次活动都要落一次盘（本机这份约 67 KB 的 JSON）。顺序已经正确时不写——`nextMove()` 返回
  `null`，这一轮没有 `insertBefore` 调用。
- 因为写的是持久顺序，用户手动拖出来的位置会被下一次活动覆盖。这一点写进了 README 的「取舍与限制」，
  并在插件说明里点明「想完全手动控制就关掉本插件」。
- 事件之间的合并靠 `debounceMs`（默认 600 毫秒）：连续发消息只排一次，不会一条消息一次写盘。
